# Паттерны в ИС агентства недвижимости

## Порождающие

### Builder (`ListingBuilder`)

**Для чего:** пошагово собрать карточку объявления (название, адрес, цена, площадь, этаж / участок / назначение).

**Почему:** у объявления много полей, часть опциональна по типу. Builder позволяет собирать объект по цепочке вызовов и в конце одной проверкой убедиться, что обязательные данные есть, без гигантского конструктора с десятком параметров.

Код: `app/patterns/creational/listing.py`

### Factory Method (`factory_for(kind)`)

**Для чего:** создавать объект недвижимости разного типа — квартира, дом, коммерция — с разными правилами.

**Почему:** у квартиры обязателен этаж, у дома — участок, у коммерции — назначение. Одна функция «создать property» не подходит: логику вынесли в отдельные фабрики, а выбор типа — через `kind`. Это ровно задание: разные правила создания в одной предметке.

Код: `app/patterns/creational/listing.py`

## Структурные

### Adapter (`AddressAdapter`)

**Для чего:** принять адрес из старой CRM в виде `Город|Улица|Дом` и превратить в нормальный адрес для каталога (г. Пермь, ул. Ленина, д. 10).

**Почему:** при внедрении новой ИС часто тянут устаревший формат данных. Менять весь ввод не хотят — адаптер стыкует старое представление с новой моделью без переписывания Builder и БД.

Код: `app/patterns/structural/address.py`

### Decorator (`AuditedDealService`)

**Для чего:** при открытии и смене статуса сделки дополнительно писать запись в журнал аудита (`AuditLog`).

**Почему:** сама операция со сделкой (статус) — одна ответственность; протоколирование — другая. Decorator оборачивает базовый `DealOperations` и добавляет аудит без копипасты «и статус, и запись в лог» в каждом месте.

Код: `app/patterns/structural/deal_audit.py`

### Facade (`AgencyFacade`)

**Для чего:** дать агенту (и API) один вход: опубликовать объект, открыть сделку, перевести статус.

**Почему:** внутри задействованы Builder, Adapter, Factory, Strategy, State, Decorator, Observer. Если вызывать всё из контроллера — каша. Фасад скрывает детали и оставляет бизнес-сценарий агентства, как в задании «задача из предметной области».

Код: `app/patterns/structural/facade.py`

## Поведенческие

### Strategy (комиссия `percent` / `fixed`)

**Для чего:** считать комиссию агентства либо 3% от суммы, либо фикс 50 000 ₽.

**Почему:** политика комиссии может меняться или зависеть от договора. Вместо ветвлений по всему коду — взаимозаменяемые стратегии с одним интерфейсом `calculate(amount)`. Новую формулу проще добавить отдельным классом.

Код: `app/patterns/behavioral/commission.py`

### State (статусы сделки)

**Для чего:** вести сделку по цепочке `new` → `in_progress` → `closed` и запретить некорректные переходы (например, дальше после `closed`).

**Почему:** у сделки в агентстве есть жизненный цикл. Правила переходов — не случайные `if`, а явная модель состояний: в учебной реализации это таблица переходов и классы состояний.

Код: `app/patterns/behavioral/state.py`

### Observer (`DealEventSubject` + каналы `agent` / `journal`)

**Для чего:** после события по сделке (открыли, сменили статус) разослать уведомления — агенту и в журнал агентства (`Notification`).

**Почему:** одно событие, несколько получателей. Observer не привязывает логику сделки к «куда писать сообщение»: подписчики добавляются отдельно (канал агента, внутренний журнал), как в реальной ИС (push, email, лог).

Код: `app/patterns/behavioral/observers.py`
